    # 小微商户智能客服 RAG 系统

## 一、项目概述

### 1. 项目背景

针对小微商户在套餐咨询、营业时间、预约方式、服务介绍等场景下存在的人工客服成本较高、业务信息分散以及重复咨询较多等问题，设计并实现了一套基于 **RAG（Retrieval-Augmented Generation，检索增强生成）** 的本地智能客服系统。

系统以商户 Markdown 文档作为私有知识库，通过文档解析、语义分块、Embedding 向量化、向量数据库召回、Reranker 重排序以及本地大模型生成，实现基于商户真实业务知识的智能问答。

项目开发过程中并非一次完成，而是针对实际测试中出现的**回答不准确、知识召回失败、上下文噪声以及响应速度较慢**等问题，对 RAG 各个环节进行逐步定位和优化，最终形成了较完整的多阶段 RAG 检索架构。

---

# 二、项目最初版本

## 1. 初始目标

项目最初的核心目标是：

> 让本地大模型能够读取商户自己的业务知识，并根据知识库回答用户问题。

例如知识库中存在：

```text
A体验私教课
价格：199元
课时：60分钟
有效期：购买后30天
```

用户输入：

```text
A体验私教课多少钱？
```

系统应该能够从知识库中检索到对应内容，再让 LLM 根据检索结果生成回答。

---

## 2. 初始 RAG 架构

最初采用比较基础的 RAG 流程：

```text
Markdown 知识库
      ↓
文本分块 Chunk
      ↓
Embedding
      ↓
向量数据库
      ↓
用户问题向量化
      ↓
Similarity Search
      ↓
Top-K
      ↓
LLM
      ↓
最终回答
```

即：

```text
Query
 ↓
Embedding
 ↓
Vector Search
 ↓
Top-K Context
 ↓
LLM
 ↓
Answer
```

这个版本首先解决了一个核心问题：

> 通用大模型本身并不了解具体商户的私有业务信息，因此通过 RAG 将商户知识库动态提供给模型。

---

# 三、第一次问题：回答能够生成，但稳定性不足

## 1. 测试过程中发现的问题

基础版本可以正常运行，但是在实际测试过程中发现：

* 简单事实型问题通常可以正常回答；
* 问题表达方式发生变化后，检索结果可能发生变化；
* 部分问题虽然知识库中存在答案，但是没有召回正确内容；
* 多条件、多实体问题容易出现信息缺失；
* 检索结果中存在语义相似但实际无关的内容；
* 最终 LLM 有时会基于不完整 Context 生成不准确回答。

例如测试：

```text
有哪些预约方式？
```

或者：

```text
介绍一下这几个套餐的具体信息。
```

发现系统并不是每次都能够把最相关的知识交给 LLM。

---

## 2. 最初的错误定位

最开始容易将问题归因于：

> “是不是 LLM 能力不够？”

但进一步分析 RAG 链路后发现：

```text
最终回答错误
        ↓
不一定是 LLM 的问题
        ↓
可能是 Context 本身错误
        ↓
可能是 Retrieval 出现问题
```

因此开始将整个系统拆成：

```text
知识库
 ↓
Chunk
 ↓
Embedding
 ↓
Vector Retrieval
 ↓
Context
 ↓
Prompt
 ↓
LLM
```

逐层分析问题。

这是项目第一次重要的思路变化：

> **从单纯关注“模型回答效果”，转向分析整个 RAG 检索链路。**

---

# 四、第二次改进：优化知识库

## 1. 发现知识库本身也是影响 RAG 效果的重要因素

RAG 并不能弥补知识库本身的信息缺失。

例如：

```markdown
## 套餐

A套餐 199元
B套餐 399元
```

用户问：

```text
A套餐有几节课？
```

如果知识库没有记录课时，那么无论 Embedding、Reranker 或 LLM 多强，都无法可靠地从知识库得到答案。

因此开始对商户知识库进行扩充和结构化整理。

---

## 2. 知识库优化方向

围绕实际商户业务，将知识划分为多个业务主题，例如：

```text
套餐信息
├── 套餐名称
├── 价格
├── 课时
├── 有效期
├── 适用人群
└── 注意事项

服务信息
├── 健身私教
├── 肩颈理疗
└── 服务流程

门店信息
├── 营业时间
├── 地址
└── 联系方式

预约信息
├── 微信预约
├── 电话预约
└── 到店预约

售后信息
├── 改期
├── 取消
└── 退款相关规则
```

---

## 3. 这一步解决的问题

从：

```text
简单测试数据
```

逐渐转变为：

```text
结构化商户知识库
```

目的不是单纯增加文本量，而是：

> **让知识库中的业务知识具有完整的语义和明确的业务边界，从数据源层面提高 RAG 的可检索性。**

---

# 五、第三次改进：优化 Chunking

## 1. 发现 Chunk 是影响检索效果的重要因素

在进一步测试后发现：

> 有些问题知识库中明明存在，但是仍然检索不到。

于是开始分析文本分块。

假设原始知识：

```text
A体验私教课

价格：199元
课时：60分钟
有效期：购买后30天
适合首次体验私教服务的客户。
```

如果简单按照固定长度进行切分，可能变成：

```text
Chunk 1：
A体验私教课
价格：199元

Chunk 2：
课时：60分钟
有效期：购买后30天
适合首次体验私教服务的客户。
```

此时用户问：

```text
A体验私教课有效期多久？
```

向量检索可能只召回 Chunk 1。

结果：

```text
知识库存在答案
        ↓
Chunk 被拆散
        ↓
正确答案没有进入候选结果
        ↓
LLM 无法得到完整信息
```

---

# 六、Chunking 策略优化

## 1. 从固定长度切分转向语义化切分

优化后的核心思想：

> 不单纯根据字符数量切分，而是尽可能根据 Markdown 层级和业务语义进行切分。

例如：

```markdown
## A体验私教课

- 价格：199元
- 课时：60分钟
- 有效期：30天
- 适合人群：首次体验客户
- 注意事项：需提前预约
```

尽可能作为一个完整的知识单元。

---

## 2. Chunk 设计原则

### Chunk 太小

容易导致：

```text
一个业务实体
 ↓
被拆成多个 Chunk
 ↓
相关信息相互分离
```

导致上下文不完整。

---

### Chunk 太大

可能导致：

```text
一个 Chunk
 ↓
包含多个不同业务主题
 ↓
产生大量无关信息
```

从而增加检索噪声。

---

## 3. 最终目标

因此 Chunking 的目标变成：

```text
业务语义完整
+
信息粒度适中
+
减少无关内容
+
方便后续检索
```

这一阶段主要解决：

> **知识信息被错误切分，以及检索结果上下文不完整的问题。**

---

# 七、第四次改进：优化 Embedding

## 1. 发现关键词匹配无法覆盖用户表达

例如用户问：

```text
怎么预约？
```

知识库可能写：

```text
客户可以通过微信、电话或者到店的方式提前预约。
```

二者表达方式不同。

如果只依赖关键词：

```text
怎么预约
```

和：

```text
微信、电话、到店
```

并不一定具有很高的文字匹配程度。

因此使用 Embedding 将 Query 和知识库 Chunk 转换为语义向量。

---

## 2. Embedding 工作方式

用户问题：

```text
怎么预约？
```

↓

```text
Query Embedding
```

知识库：

```text
客户可以通过微信、电话或者到店的方式提前预约。
```

↓

```text
Document Embedding
```

然后计算向量之间的语义相似程度。

理想情况下：

```text
“怎么预约？”
        ≈
“有哪些预约方式？”
        ≈
“如何进行预约？”
        ≈
“可以通过什么渠道进行预约？”
```

---

## 3. Embedding 优化的核心

开始关注：

* 中文语义理解能力；
* Query 与 Document 的语义匹配；
* Embedding 模型对客服领域问题的适应性；
* Embedding 模型对召回结果的影响。

因此逐渐认识到：

> **Embedding 并不是简单的数据预处理组件，而是直接决定向量召回质量的核心环节。**

---

# 八、第五次改进：调整 Top-K 召回策略

## 1. Top-K 太小的问题

例如：

```text
Top-K = 2
```

可能：

```text
候选结果：
① 无关但相似内容
② 边缘相关内容
```

真正答案没有进入候选集。

也就是：

```text
K 太小
 ↓
候选集覆盖不足
 ↓
正确知识可能被漏掉
```

---

## 2. Top-K 太大的问题

例如：

```text
Top-K = 10
```

可能召回：

```text
正确答案
相关答案
边缘相关答案
无关答案
重复信息
```

全部进入 LLM Context。

导致：

```text
Context 变长
 ↓
无关信息增加
 ↓
模型需要自行筛选
 ↓
推理成本增加
 ↓
回答可能受到噪声影响
```

---

## 3. 因此改变设计思路

不再让：

```text
Vector Search
```

直接决定最终 Context。

而是：

```text
Vector Search
       ↓
候选集
       ↓
再次筛选
       ↓
最终 Context
```

即：

> **向量检索主要负责提高召回覆盖率，而不是直接决定最终答案。**

这个改变为后续引入 Reranker 做了基础。

---

# 九、第六次改进：引入 Reranker 二阶段检索

## 1. 初始架构

```text
Query
 ↓
Embedding
 ↓
Vector Search
 ↓
Top-K
 ↓
LLM
```

问题在于：

> 向量相似度高，不一定代表对当前 Query 真正相关。

---

## 2. 升级后的架构

```text
Query
 ↓
Embedding
 ↓
Vector Search
 ↓
Top-K Candidate
 ↓
Reranker
 ↓
Top-N
 ↓
LLM
```

形成：

```text
第一阶段：
Vector Search
↓
高召回

第二阶段：
Reranker
↓
高相关
```

---

# 十、为什么使用二阶段检索

例如用户问题：

```text
私教课多少钱？
```

向量搜索可能召回：

```text
① A体验私教课
② B进阶私教课
③ 私教服务介绍
④ 私教预约方式
⑤ 肩颈理疗套餐
```

这些文本可能都具有一定的语义相似性。

但是 Reranker 进一步对：

```text
Query
+
Candidate Document
```

进行相关性判断。

最终按照相关程度重新排序。

因此：

```text
Vector Search
负责：
“从大量知识中找出可能相关的候选”

Reranker
负责：
“判断候选内容和当前问题到底有多相关”
```

---

# 十一、二阶段检索带来的架构变化

系统从：

```text
一次检索
 ↓
直接回答
```

升级成：

```text
粗召回
 ↓
候选集
 ↓
精排
 ↓
高相关知识
 ↓
LLM
```

这使整个 RAG 检索过程更加可控。

核心策略可以概括为：

> **Recall First，Precision Later。**

即：

> 第一阶段尽量不要过早丢掉可能正确的知识；第二阶段再进行精细筛选。

---

# 十二、第七次改进：优化 Context

引入 Reranker 后，又发现：

> 即使已经排序，最终也不能简单地把所有候选内容全部交给 LLM。

因此增加了 Context 筛选思路。

完整流程变成：

```text
Vector Search
 ↓
Top-K
 ↓
Reranker
 ↓
重新排序
 ↓
Top-N
 ↓
Context Selection
 ↓
LLM
```

---

## Context 优化目标

尽可能做到：

```text
高相关
+
低噪声
+
信息完整
+
长度可控
```

减少：

```text
重复 Chunk
低相关 Chunk
边缘相关信息
```

进入最终 Prompt。

---

# 十三、第八次改进：优化 Prompt 与回答行为

即使检索结果正确，也可能出现：

```text
Context 正确
 ↓
LLM 回答不理想
```

例如知识库：

```text
周一至周五：09:00-21:00
周六至周日：10:00-20:00
```

用户：

```text
周一几点开门？
```

理想情况下只需要回答：

```text
周一 09:00 开门。
```

因此对 Prompt 进行约束，使模型：

* 优先依据检索结果回答；
* 不随意补充知识库不存在的信息；
* 减少无关内容；
* 根据用户问题控制回答范围；
* 在知识库缺少信息时避免直接编造。

核心目标：

```text
Retrieved Context
       ↓
Prompt约束
       ↓
LLM
       ↓
更稳定的客服回答
```

---

# 十四、第九次改进：本地 LLM 模型测试

在检索链路逐渐稳定之后，进一步发现：

> 检索正确并不代表最终回答一定正确。

因为最终仍然依赖 LLM 对：

```text
用户问题
+
检索 Context
+
Prompt
```

进行理解和生成。

因此开始使用 Ollama 进行本地模型部署和测试。

---

## LLM 与 Embedding 的职责区分

项目中逐渐明确两个模型承担不同职责：

```text
Embedding Model
       ↓
负责：
Query 与 Document 的语义匹配
       ↓
影响 Retrieval
```

而：

```text
LLM
       ↓
负责：
理解 Query
+
理解 Context
+
组织最终回答
       ↓
影响 Generation
```

因此：

```text
Embedding 不好
→ 可能找不到正确知识

LLM 不合适
→ 可能找到正确知识但回答质量不理想
```

这使模型优化不再简单地理解成：

> “换一个更大的模型。”

而是开始根据：

```text
回答质量
+
推理速度
+
本地资源
+
任务复杂度
```

综合进行模型测试。

---

# 十五、第十次改进：开始进行性能分析

当回答质量逐渐稳定之后，新的问题出现：

> **系统响应速度较慢。**

这时候发现一次 RAG 请求实际上包含多个计算阶段：

```text
用户 Query
 ↓
Embedding
 ↓
Vector Search
 ↓
Reranker
 ↓
Context 组装
 ↓
Prompt
 ↓
LLM
 ↓
Token Generation
```

因此不能简单地认为：

> “RAG 慢。”

而应该进一步拆解：

```text
T_total
=
T_embedding
+
T_retrieval
+
T_rerank
+
T_context
+
T_LLM
```

---

# 十六、性能优化思路

开始针对每一个阶段分别观察耗时。

例如：

```text
Embedding
   ↓
耗时多少？

Vector Search
   ↓
耗时多少？

Reranker
   ↓
耗时多少？

LLM
   ↓
耗时多少？
```

这样可以进一步判断：

```text
系统慢
```

究竟是：

```text
Embedding慢
```

还是：

```text
Reranker慢
```

或者：

```text
LLM推理慢
```

---

## 性能优化方向

围绕实际运行情况，逐步考虑：

```text
模型大小
+
Embedding耗时
+
Reranker候选数量
+
最终Context长度
+
LLM推理速度
```

最终从单纯关注：

> 回答是否正确

进一步发展到：

> **回答质量与系统响应速度同时优化。**

---

# 十七、最终形成的 RAG 架构

经过多轮优化，目前系统的核心思路已经从最初的：

```text
Vector Search + LLM
```

演进为：

```text
                    Markdown知识库
                           ↓
                       文档解析
                           ↓
                    结构化语义分块
                           ↓
                       Embedding
                           ↓
                    ┌─────────────┐
                    │ Vector DB   │
                    └──────┬──────┘
                           ↑
                           │
                        用户Query
                           ↓
                     Query Embedding
                           ↓
                    Top-K向量召回
                           ↓
                     候选知识集合
                           ↓
                       Reranker
                           ↓
                     二次相关性排序
                           ↓
                      Top-N结果
                           ↓
                    Context Selection
                           ↓
                        Prompt
                           ↓
                     本地 Ollama LLM
                           ↓
                       最终回答
```

---

# 十八、项目解决的问题

## 1. 私有知识无法被大模型直接利用

### 原问题

通用 LLM 不掌握具体商户的实时业务信息。

### 解决方案

引入 RAG：

```text
商户知识库
+
向量检索
+
LLM
```

### 改进结果

使模型能够根据商户私有知识进行回答。

## 2. 知识库中有答案但检索不到

# 二十、项目最大的技术思路变化

整个项目最重要的变化并不是简单增加了几个组件，而是**问题定位方式发生了变化**。

最开始：

```text
回答错误
 ↓
怀疑 LLM
 ↓
考虑换模型
```

逐渐变成：

```text
回答错误
 ↓
检查 Context
 ↓
检查 Retrieval
 ↓
检查 Reranker
 ↓
检查 Chunk
 ↓
检查 Embedding
 ↓
检查 Prompt
 ↓
最后再检查 LLM
```

最终形成了一套比较完整的 RAG 问题排查链路：

```text
① 知识库是否存在答案？
        ↓
② Chunk 是否保持信息完整？
        ↓
③ Embedding 是否正确表达语义？
        ↓
④ Vector Search 是否召回？
        ↓
⑤ 正确 Chunk 的召回排名是多少？
        ↓
⑥ Reranker 是否正确排序？
        ↓
⑦ 最终 Context 是否包含正确知识？
        ↓
⑧ Prompt 是否正确约束模型？
        ↓
⑨ LLM 是否正确利用 Context？
```

这也是项目开发过程中最重要的工程经验之一。
